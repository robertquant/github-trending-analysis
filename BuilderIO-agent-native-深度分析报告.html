📋 项目概述

Agent-Native 是 Builder.io 推出的开源框架，用于构建所谓的「代理原生（Agent-Native）应用」——这是一类从架构底层就让人类用户与 AI Agent 能够操作同一个产品的应用。它不把 AI 当做事后「贴上去」的功能，而是让 UI 与 Agent 成为同一套系统中的「平等公民」。

项目背后的核心理念用一句话概括："Click it or ask for it"（点击它，或者用自然语言请求它）。同一个产品能力，既能在可视化界面里点击触发，也能被 Agent 通过工具调用执行，二者背后共享同一份动作定义、同一份数据状态、同一套权限与上下文。

💡 一句话定位
它不是又一个 LLM 编排框架，而是一种新的软件架构范式 + 一套脚手架。它解决的是「精美但僵化的 SaaS」与「强大但空白的裸 Agent」之间的长期割裂——把 SaaS 的产品形态与 Agent 的灵活性合二为一。

核心一句话价值主张

  • Agents and UIs — Fully Connected：Agent 与 UI 完全互通，同一个动作双向可用。
  • Backend Agnostic：后端无关，自带数据库、托管、模型栈皆可替换。
  • One agent, three shapes：同一个 Agent 可发布为无头 API、富聊天、完整应用三种形态。
  • Apps that improve themselves：应用能自我演进——Agent 可自行加功能、修 bug、优化 UI。

🧭 背景与动机：为什么需要「Agent-Native」

Builder.io CEO Steve Sewell 在系列博客中提出，今天的软件普遍给开发者一个两难妥协：

选项做得好的破绽真正想要的
传统 SaaS精美 UI、清晰流程、团队易上手Agent 接入是局部的、被「贴」上去的一个 Agent 能完整操作的真正 UI
裸 Agent（Claude Projects 等）灵活、强大、自然语言可控空白画布、缺乏产品形态、无流程引导带产品结构的 Agent 能力
内部工具定制逻辑与数据访问维护负担重，AI 是事后加的Agent 作为核心的定制软件
Agent-Native 应用UI 与 Agent 共享同一套应用模型需要不同的架构人机协作、无需妥协

因此「贴在角落的聊天机器人」迟早会撞到天花板：它能总结文档、起草回复，却无法可靠地看到相同的状态、走相同的工作流、用相同的底层原语去改变产品。

软件演化的三阶「梯子」

STAGE 1
AI-Enabled（AI 辅助）
产品有 AI 功能，但去掉 AI 产品仍基本可用。
例：带 AI 摘要按钮的项目管理工具。
➜
STAGE 2
AI-Native（AI 原生）
AI 是产品价值的核心，去掉 AI 产品就垮。
例：编码助手、图像生成器、聊天优先的研究工具。
➜
STAGE 3
Agent-Native（代理原生）
AI 是核心，且产品仍拥有完整的、与 Agent 共享动作/数据/权限的人机界面。
例：邮件客户端——人手动分类，Agent 通过相同动作归档/起草/打标/路由。

关键洞察：Agent-Native 比 AI-Native 更具体——它不仅要求 AI 居中，还要求产品拥有一个真实的人机界面，且二者共享对应用能力的完整访问。

🏗️ 技术架构

框架提供一组面向「产品级 Agentic 软件」的原语：共享动作（actions）、SQL 驱动的状态、身份（identity）、工具（tools）、技能（skills）、任务（jobs）、可观测性（observability），以及与之协同的 UI 表面。后端完全可替换——自带任何 Drizzle 支持的 SQL 数据库、任何 Nitro 兼容的托管目标。

① 核心原语：统一动作模型（One Action Model）

这是整个框架的「灵魂」。一次定义，多面暴露——同一个 Action 自动成为 UI 变更、Agent 工具、HTTP 端点、CLI 命令、MCP 工具和 A2A 工具。

// actions/reply-to-email.ts —— 一次定义，六处复用
import { defineAction } from "@agent-native/core";
import { z } from "zod";

export default defineAction({
  description: "Reply to an email thread",
  schema: z.object({
    emailId: z.string(),
    body: z.string(),
  }),
  run: async ({ emailId, body }) => {
    await db.replies.insert({ emailId, body });
  },
});

传统做法里，团队要分别实现 UI 动作、API 端点、自动化钩子、LLM 工具定义、CLI 命令，再加文档解释它们的关系——每一份拷贝都会产生漂移（drift）。Agent-Native 用「单一动作定义」从源头消灭这种漂移。

② 五大架构原则

1
Agent UI Parity（代理-界面对等）
UI 能做的，Agent 也能做；Agent 做的事也应可通过界面/日志/权限/状态被看见、检查或控制。Agent 不应去「屏幕抓取」UI，而应调用驱动产品的同一底层能力。
2
One Shared Action Model（统一动作模型）
能力只定义一次（归档邮件、创建仪表盘、渲染视频、安排会议…），随后暴露给每一个需要的表面。
3
Shared State, Data & Context（共享状态与上下文）
Agent 知道你在看什么、选中了什么、哪些筛选生效。UI 把导航状态写下来，view-screen 动作给 Agent 当前视图快照，navigate 动作让 Agent 移动 UI。数据库是人与 Agent 之间的协调层——动作写 SQL，版本变化，UI 轮询并失效对应数据。
4
Protocol-Ready by Design（协议就绪）
应用是软件节点，可被其他 Agent 与 App 使用。协议支持（MCP、A2A）是架构属性而非一次性集成项目——既然 actions 已是共享的行为单元，把它们暴露给 MCP/A2A/CLI 只是「路由问题」。
5
Governed Execution（受治理的执行）
Agent 能在你无权访问的客户记录上动手吗？不能。发邮件/删文件/发布页面需要确认的，Agent 同样遵守边界。产品应暴露日志、审计轨迹、状态变更供人检查——Agent 强大，因为能行动；产品可信，因为这些行动可被限定、可回溯、必要时可撤销。

③ 实时多人协作 & 工作区

🔀 Real-time Multiplayer
人与 Agent 在同一文档实时协作：CRDT 合并、实时存在感（光标、选区高亮、谁在哪一页），Agent 是一等「对等编辑者」。可在任何 SQL 数据库与任何主机（含 Serverless）上运行。
🗄️ SQL-backed Workspace
技能、记忆、指令、子 Agent、MCP 服务器——全部 SQL 化、按用户/组织定制。把 Claude Code 级别的灵活性带进产品本身，且具备 SaaS 级的经济性。
🤝 Agents Call Agents
从任一 App 标记另一个 Agent，它们通过 A2A 协议互相发现，跨越你的整个技术栈采取行动。
🔐 Reusable Integrations
在 Dispatch 里连接一次供应商，密钥存入 vault，再把账户元数据与凭证引用授权给 Brain/Analytics/Mail 等多个 App 共享。

④ 技术栈与协议支持

  • 语言/运行时：TypeScript；数据库经由 Drizzle ORM（任意 SQL）；托管经由 Nitro（Vercel/Cloudflare/Node 等）。
  • 内建协议：A2A、MCP、MCP Apps、标准远程 MCP OAuth、MCP 客户端、HTTP/CLI 动作调用、原生聊天组件、AgentChatRuntime 适配器。
  • 兼容运行时：标准 OpenAI、AG-UI、Claude Agent SDK、Vercel AI SDK 的聊天运行时连接器。
  • 编码 Agent 接入：Claude Code、Codex、Cursor、Pi、OpenCode、GitHub Copilot / VS Code 等 MCP 兼容宿主可直接操作你托管的应用。

🧩 一个 Agent，三种产品形态

Agent-Native 原语让你无需重建 Agent 契约，就能选择给 Agent「裹」多少 UI：

🟣 Headless（无头）
从代码/CLI/HTTP/MCP/A2A 调用 Agent 与动作。底层共享 defineAction、auth、skills、memory、jobs、observability。
🟢 Rich Chat（富聊天）
独立或嵌入式聊天，原生支持表格、图表、审批、设置流与工具结果。共享聊天运行时 + BYO 运行时适配器 + 动作声明的原生渲染器。
🔵 Whole App（完整应用）
完整 SaaS/产品 UI——聊天可居中、可移到侧栏，始终与应用状态同步。SQL 状态、动作、上下文感知、深链、实时同步全开。
🎯 设计哲学
协议随框架「附赠」，而不是每个功能都要做一次单独集成。今天这意味着 A2A、MCP、AG-UI、Claude Agent SDK、Vercel AI SDK 等都挂在「同一个动作表面」上。

✨ 核心创新点

① Action 即「单一事实来源」
用 defineAction 把产品能力收敛为一个定义，消灭 UI/API/工具/CLI 之间的漂移。这是对传统「每个表面各写一份」的根本性重构。
② 数据库作为协调层
人与 Agent 不靠脆弱的浏览器自动化或长连接基础设施同步，而是都读写同一份 SQL 状态——版本变化即触发 UI 失效更新。简洁、可移植、可审计。
③ 可克隆的 SaaS（Cloneable Apps）
每个模板都是可 fork 的完整开源 SaaS——拥有代码、拥有数据库、当默认形态不合身时直接改造。打破「一刀切」SaaS 的所有权困局。
④ 零配置跨应用 A2A
同源部署带来共享登录会话与零配置跨应用 A2A——在日历的 Agent 聊天里 @mail 就能直接调起邮件 Agent，无需 JWT 签名、无需 CORS。
⑤ 应用自我演进
Agent 可在不发版的情况下给 App 加功能、修 bug、优化 UI——「运行时工具」让 Agent 在 App 内创建临时仪表盘/计算器/监控，成熟后再「毕业」为模板特性。
⑥ SQL 化的工作区经济
AGENTS.md 指令、LEARNINGS.md 记忆、技能、子 Agent、定时任务都存在 SQL 而非本地文件系统——把 Claude Code 的开发级体验带进 SaaS 经济模型。

🚀 应用场景

框架已提供多个可克隆的完整模板，覆盖常见 SaaS 品类：

模板对标产品Agent 在其中的角色
📅 CalendarGoogle Calendar / Calendly管理日程、同步、AI 排程、公开预约页
📝 Content开源版 Obsidian（MDX）编辑本地 MD/MDX、生成富交互块、起草/改写/发布
🗂️ Plans编码 Agent 的可视化计划模式/visual-plan 与 /visual-recap 技能
🎤 SlidesGoogle Slides / Pitch提示词或点击生成、编辑基于 React 的演示文稿
📊 AnalyticsAmplitude / Mixpanel连接数据源、提示生成图表、构建可复用仪表盘
🎬 ClipsLoom录屏+自动转录+分享链接，Agent 摘要/字幕/编辑
✉️ Mail / 📋 Forms邮件 / 表单 SaaS三步邮件分诊、跨系统拉取上下文、自动路由

典型落地路径

  • 个人开发者（周末克隆）：用自带 LLM Key 克隆模板，跑真实个人工作流；当 SaaS 不再能回答「晚上8点后吃什么和我的糟糕睡眠相关吗」这类原始开发者没想到的问题时，自有数据库 + Agent 让你直接发问。
  • 团队规模化：当模板值得共享，问题从「我能用吗」转向「团队能信任吗」——需要托管、数据库管理、鉴权、权限、分支、治理与共享密钥。Builder.io 即承担这层「团队层」。
  • Agent 生态互联：分析 App 可请幻灯片 App 把仪表盘变成演示文稿；日历 App 可与邮件 App 协调提议会议时间；Dispatch Agent 可跨 App 生态路由工作，无需各自写胶水代码。

⚡ 快速开始

# 一条命令 fork 模板并本地构建（多选 picker 可在一个 workspace 装多个 app）
npx @agent-native/core@latest create my-platform
cd my-platform && pnpm install && pnpm dev

# 单 App、不要 monorepo：
npx @agent-native/core@latest create my-app --standalone --template mail

# 还没准备好建整个 App？给编码 Agent 加一个技能：
npx @agent-native/core@latest skills add visual-plan

# 同源部署多个 App，共享登录 + 零配置跨应用 A2A
npx @agent-native/core@latest deploy
🧠 两个开箱即用的 Slash 命令
/visual-plan：写代码前先打开结构化、可评审的计划文档（内联图表、UI 线框、文件级实现地图、可评论可批准）。
/visual-recap：把 PR/git diff 变成高视角的可视化回顾（schema、API、文件变更的前后对比块 + 可分享评审链接）。

⚔️ 竞品对比

「代理原生」横跨了 Agent 编排框架、AI 应用构建器、应用内 AI 等多个赛道，但定位独特。

方案UI 质量AI/Agent可定制所有权核心差异
传统 SaaS（Notion/Linear…）精美但僵化外挂式几乎不能租用Agent 只能「旁白」
裸 Agent（Claude Projects）无强大指令/技能半自有空白画布、无产品形态
AI 应用构建器（Bolt/Lovable/v0）生成 UI生成式代码可改自有偏「一次生成」，缺运行时 Agent-UI 同步
CopilotKit / 应用内 AI SDK嵌入组件聊天优先组件级自有把 AI 嵌进现有 App，非 Agent-Native 架构
LangGraph / Mastra / VoltAgent无内置编排强大高自有专注 Agent 编排，UI/产品形态需自建
Agent-Native完整 UI、fork 即用Agent 优先、深度集成Agent 直接改 App自有代码+数据UI 与 Agent 共享同一动作表面
🔎 真正的护城河
竞品多在「单点」上很强——要么生成 UI、要么编排 Agent、要么把 AI 嵌进现有 App。Agent-Native 的稀缺之处在于架构层面就强制 Agent 与 UI 对等，并以「可克隆 SaaS + 统一动作模型」给出了从个人到团队的可落地路径，而非停留在 SDK 层。

⚖️ 综合评估

✅ 优势

  • 概念前瞻：「Agent-Native」准确命名了一个正在发生的需求——Agent 不能只做「旁白」，要能真正操作产品。
  • 架构优雅：defineAction + 数据库协调层，从源头消灭多表面漂移，简洁且可移植。
  • 开箱即用：Calendar/Slides/Analytics/Clips 等多个可克隆完整 SaaS，显著降低上手门槛。
  • 生态站位好：原生拥抱 MCP/A2A/AG-UI，与 Claude Code/Cursor 等主流编码 Agent 打通。
  • 商业闭环清晰：开源框架 + Builder.io 团队层托管/治理，有可持续变现路径。

⚠️ 风险与挑战

  • 较新、尚处早期：约 1.1k Stars，API 与模板仍在快速演进，生产采用需评估稳定性。
  • 概念推广成本：「Agent-Native vs AI-Native」的区分需要教育市场，可能被泛化为营销词。
  • 框架锁定倾向：深度依赖 @agent-native/core 的动作/运行时抽象，迁移成本存在。
  • 安全面扩大：Agent 拥有与用户等同的操作能力，「受治理执行」一旦配置疏漏，风险被放大。

🎯 适合谁

  • 想构建「人机协作型 SaaS」、且希望拥有代码与数据的独立开发者 / 初创团队。
  • 需要把内部工具「Agent 化」、又不想从零搭 UI 的工程团队。
  • 希望在自家产品中嵌入真正能操作产品的 Agent（而非聊天旁白）的产品团队。

🏁 结论

Agent-Native 不只是一个框架，更是 Builder.io 对「下一代软件架构」的一次押注：未来的应用，人能做的 Agent 也能做，且共享同一套动作、数据与权限。它用统一动作模型、数据库协调层和可克隆 SaaS，把抽象理念落成了可 fork、可改造、可托管的工程现实。

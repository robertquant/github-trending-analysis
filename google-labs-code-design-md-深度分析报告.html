项目概述

DESIGN.md 是 Google Labs（google-labs-code 组织）推出的一个格式规范（format specification）项目，其核心目标是：为编码 Agent（coding agents）描述一套视觉识别系统（visual identity）的开放文件格式。换句话说，它定义了一种结构化的 Markdown 文件，让 Claude Code、Cursor 等 AI 编码工具能够获得对设计系统（design system）的持久化、结构化理解。

该项目脱胎于 Google 的 AI UI 设计工具 Stitch（前身为 Galileo AI）。Stitch 是一款 Gemini 驱动的"AI 原生 UI 设计工具"，能从文本、图像或草图生成多屏响应式界面。在实践过程中，Google 团队发现："如何把设计系统的规则稳定地传递给下游编码 Agent" 是设计到代码流程中最大的痛点。于是他们把 Stitch 内部使用的 DESIGN.md 文件格式抽离、规范化，于 2025 年底以 Apache-2.0 协议正式开源，并配套发布了 TypeScript 编写的校验 / 导出 CLI（@google/design.md）。

"DESIGN.md gives agents a persistent, structured understanding of a design system. Tokens give agents exact values. Prose tells them why those values exist and how to apply them." —— Google Labs

凭借 Google 的背书、直击"AI 生成 UI 千篇一律（AI-looking slop）"痛点的定位，以及与 Claude Code、Cursor、Stitch 等主流工具的无缝衔接，DESIGN.md 在极短时间内 GitHub Star 飙升至 1.8 万+，并被多家行业媒体称为"正走向行业标准化的开放格式"。它本质上不是一款产品，而是一份约定 + 一套工具链——一种让设计系统能像代码一样被 AI 读懂、被 Git 版本化、被多工具互操作的"通用语言"。

技术架构

DESIGN.md 的设计哲学是 "一份文件、两层结构"：上半部分是机器可读的设计 Token（YAML front matter），下半部分是人类可读的设计理念（Markdown 正文）。Token 给 Agent 提供精确的数值，正文告诉它这些数值为什么存在以及如何应用。

📐 Token Schema（规范性字段）

version: "alpha"          # 可选，当前版本
name: <string>
colors:     # 任意 CSS 颜色：hex / rgb() / oklch() / 命名色
  <token>: <Color>
typography: # 对象：fontFamily / fontSize / fontWeight / lineHeight ...
  <token>: <Typography>
components: # 组件 = 一组子 token（可用 {path.to.token} 引用）
  button-primary:
    backgroundColor: "{colors.tertiary}"
    textColor: "{colors.on-tertiary}"
    rounded: "{rounded.sm}"
⚙️ 章节顺序约定：正文 ## 标题须按 Overview → Colors → Typography → Layout → Elevation & Depth → Shapes → Components → Do's and Don'ts 的规范顺序排列，可省略但顺序不可乱。消费端对未知内容采取宽容策略（未知色名/排版名视为有效，仅未知组件属性给出 warning），只有重复章节标题才报错拒绝。

核心创新点

🧬 "Token + 意图"双层数据模型

传统 Design Token 只有冰冷的数值，AI 仍不懂"为何如此"。DESIGN.md 把规范性 Token与解释性散文装进同一文件——Agent 既拿到精确值，也理解设计意图与边界条件，从而生成有灵魂、有取舍依据的 UI。

📄 用 Markdown 对抗二进制锁定

整个设计系统压缩进一个纯文本 .md 文件，天然可 Git 版本化、可 Diff、可 Code Review。彻底摆脱 Figma 二进制文件难以 diff、Token 散落各处的治理痛点，让设计系统首次成为"代码资产"。

🔍 9 条内建 Lint 规则

配套 linter 自动检查断链引用（broken-ref）、WCAG AA 对比度（4.5:1）、孤立 Token、缺失 primary 色、章节顺序错乱等 9 类问题，输出结构化 JSON 供 Agent 直接消费——把可访问性与一致性前移到"写设计系统"的环节。

🔀 diff 命令做"设计回归检测"

diff 子命令对比两版 DESIGN.md，报告 Token 级增删改与 prose 变化，并判定是否构成设计回归。相当于给设计系统加了"CI"，防止改版无意破坏既有视觉规范。

🔄 一键导出主流生态

export 可输出 Tailwind v3 theme.extend、Tailwind v4 @theme CSS 变量、以及 W3C Design Tokens Format Module（DTCG）标准格式。一份 DESIGN.md → 任意前端框架，跨工具互操作零摩擦。

🤖 spec 命令直注 Agent 上下文

spec 可输出规范本身，便于把 spec 上下文注入 Agent 提示词，让任意模型按统一规范生成 / 校验 DESIGN.md。配合 Stitch 导出、Claude Code 消费，形成完整闭环。

应用场景

  • Stitch → Claude Code 设计到代码交接：在 Stitch 中设计后，右侧 Design Systems 面板一键导出 DESIGN.md，丢进项目根目录或写入 CLAUDE.md，每个 Claude Code 会话都自动加载一致的设计规范，彻底修复"设计稿到代码"的割裂。最核心场景
  • 消除 AI 生成 UI 的"千篇一律"：把品牌色板、字体、间距、组件规则锁进 DESIGN.md 作为护栏，AI 生成的界面不再是通用模板风（AI slop），而是严格符合品牌识别的定制 UI。
  • 设计系统的版本化与协作：用单一 Markdown 文件作为设计系统 SSOT（单一事实来源），团队通过 Git PR 评审设计变更，diff 追踪改版、lint 守护可访问性。
  • 跨设计工具互操作：导出 W3C DTCG 标准格式，让 Token 在 Figma、Penpot、Style Dictionary 等工具间无损流转，打破单一设计软件的锁定。
  • 设计令牌治理与回归保护：在 CI 中接入 linter 与 diff，自动拦截低对比度、断链 Token、违规改版，将设计质量保障自动化。
  • AI 代码生成器 / IDE 集成：Cursor、Windsurf、各类 Agent Skills 可直接读取 DESIGN.md 生成前端代码；社区已有将其接入 Anthropic frontend-design Skill 的提案。
DESIGN.md 正成为"设计系统的 README"——设计师写意图，AI 编码 Agent 读规范，二者在同一份文件上对齐，让 Vibe Design 真正能交付一致的产品级 UI。

定位差异小结：

  • DESIGN.md — 唯一从 AI Agent 视角出发的格式，"Token + 意图 + Lint"三合一，最适合当下AI 编码工作流；劣势是处于 alpha、生态尚在起步。
  • W3C Design Tokens — 业界标准、最严谨，DESIGN.md 的 Token 模型正是受其启发并支持导出为 DTCG。强在标准化、弱在"无灵魂"。
  • Figma Variables — 设计师最熟悉的主场，但锁定在 Figma 内，需借助 MCP / 插件才能喂给 AI，治理与 diff 是短板。
  • Style Dictionary — 老牌构建期转换引擎，擅长把 Token 转成各平台代码，但不提供"设计规范"语义，是 DESIGN.md 的互补而非替代。
